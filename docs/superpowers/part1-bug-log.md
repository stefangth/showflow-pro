# Part 1 — Bug Log

Findings surfaced by deep edge-function tests. Severity: CRITICAL (data loss / security / silent failure) · HIGH (wrong result for users) · MED · LOW.

| Function | Severity | Contract violated (app-logic.md ref) | Resolution | Test |
|---|---|---|---|---|
| `send-offer-digest` | MED | at-least-once email on stamp failure — if `sendEmail` succeeds but the subsequent `bookings.update` (stamp) returns an error, the handler logs and continues without incrementing `digests_sent`. The booking retains `digest_sent_at = null` and will be re-queried on the next run, sending a duplicate offer email. The idempotency key `offer-digest-<artistId>-YYYY-MM-DDTHH` mitigates duplicates within the same UTC hour only; a stamp failure at 19:01 and a retry at the next day's 19:00 run will produce an unavoidable duplicate (different key). Doc ref: _The Offer → Booking Flow_ — "Stamps `digest_sent_at = now()` … offers will re-send next run". | design-limitation (acceptable at current scale; at-least-once delivery is the stated behavior); no code change. The harness cannot selectively fail the UPDATE without also failing the SELECT on the same table — a `// NOTE:` comment in the test documents this limitation and the verdict. | `send-offer-digest: atomicity characterization — harness limitation for stamp-failure path` |
| `expire-offers` | LOW (doc-gap) | Spec says "dedupe duplicate ids" for recipients but the handler does no deduplication. If `resolve_show_assignments` returns the same `producer_user_id` twice (possible if the RPC has its own join explosion), two `cast_escalation_requested` notifications are inserted for the same user and two emails are sent. The `send-offer-digest` handler (and `tier-at-risk-watcher`) both dedupe explicitly; `expire-offers` does not. | FIXED: added `[...new Set(recipientIds)]` for consistency with `tier-at-risk-watcher` | `expire-offers: dedupes duplicate producer ids → one notification + one email per user` |
| `tier-at-risk-watcher` | HIGH | Stale `tier_at_risk` notifications were never deleted when all open tiers closed. The handler's early-exit at `if (!openTiers || openTiers.length === 0) return json({ at_risk_count: 0 })` ran before the notification-cleanup block, so if a tier closed (got `closed_at` set) while its notification still existed, that notification persisted forever — leaving a stale "Tier at risk" warning in the UI indefinitely. Contract: _"clears when math recovers (by deleting the old row)"_ — a closed tier is definitively recovered. | FIXED: moved `notifications` query before the early-exit decision; added a combined guard `if (no open tiers AND no existing notifs)` for the true nothing-to-do case; recovery delete now runs regardless of open-tier count. Regression test: `tier-at-risk-watcher DI: stale notifications for closed tiers ARE cleared`. | `tier-at-risk-watcher DI: stale notifications for closed tiers ARE cleared (regression: was a bug)` |
| `send-transactional-email` | NONE (all contracts confirmed) | Suppression fail-closed: CONFIRMED. Suppression DB error fail-closed: CONFIRMED (handler returns 500 and does NOT call Resend). Snake_case body keys: CONFIRMED. Log non-blocking: CONFIRMED (log insert errors ignored on success path). Used-token safety fallback: CHARACTERIZATION — when `email_unsubscribe_tokens.used_at` is set but email is not in `suppressed_emails`, the handler returns `{ success: false, reason: 'email_suppressed' }` (safety fallback, line ~131). This is intentional-but-undocumented: it assumes a used token implies the user unsubscribed before the suppression row was written; blocks the send as a conservative safety measure. | No fix needed. Characterization test added with `// characterization:` comment. | `characterization: used token + not suppressed → returns { success: false, reason: 'email_suppressed' }` |
| `handle-email-unsubscribe` | HIGH | POST with an already-used token returned `{ valid: false, reason: 'already_unsubscribed' }` instead of the documented `{ success: false, reason: 'already_unsubscribed' }`. Root cause: the pre-check at line 70 used the GET-response key (`valid`) for both methods. The response body key `valid` vs `success` is load-bearing — the app's unsubscribe page distinguishes GET (validation) from POST (action) responses by checking these keys. A POST that hits the pre-check would have appeared as an unknown/truthy response to a caller expecting `success: false`. | FIXED: refactored the pre-check block so GET and POST each own their `used_at` guard, returning `{ valid: false }` and `{ success: false }` respectively. | `POST already-used token → { success: false, reason: 'already_unsubscribed' }` |
